# Happy Eyeballs Version 3: Better Connectivity Using Concurrency
https://datatracker.ietf.org/doc/draft-ietf-happy-happyeyeballs-v3/

## 1. Introduction
- 現代のインターネット上で動作する多くの通信プロトコルは、ホスト名を使用する
- ホスト名は多くの場合、複数のIPアドレスに名前解決され、それぞれが異なる性能や接続特性を持つ可能性がある
- 特定のアドレスやアドレスファミリ (IPv4またはIPv6) はネットワーク上で遮断されていたり、
  破損していたり、最適でなかったりする可能性がある
  - そのため、複数の接続を並行して試行するクライアントは、より迅速に接続を確立できる可能性がある
- 本書は、デュアルスタックホストでユーザが認識する遅延を低減する技術であるHappy Eyeballsのアルゴリズムを定義する
  - この定義は [HEV2] の記述を更新するものであり、[HEV2] 自体が [RFC6555] を置き換えたものである
- 名前解決されたエンドポイントに対して接続を競争させるHappy Eyeballsアルゴリズムは、
  ユーザへの遅延を可能な限り避けるために、いくつかの段階を持つ
  - その際IPv6の使用を優先することや、
    HTTP/3 [HTTP3] やTLS Encrypted Client Hello [ECH] といったプロトコルが利用可能であることなど、
    クライアントの優先事項を尊重する
- 本書では、接続を開始するときにDNS問い合わせをどのように開始するか、
  DNS応答で受け取った宛先アドレスのリストをどのように並べ替えるか、
  そして接続試行をどのように競争させるかについて論じる
- 本書で定義するアルゴリズムと [HEV2] の主な違いは、
  SVCB / HTTPSリソースレコード [SVCB] への対応が追加されたことである
  - SVCBレコードは、代替エンドポイント、アプリケーションプロトコルの対応状況、Encrypted Client Hello [ECH] の鍵、
    アドレスヒント、およびアクセス対象のサービスに関するその他の関連情報を提供する
  - HTTP/3 over QUIC [HTTP3] のようなプロトコルの対応状況を名前解決中に検出することで、
    HTTP Alternative Services [AltSvc] などの他の検出メカニズムの情報を使って後続の試行を行うのを待つのではなく、
    現在の接続試行の中でプロトコルをアップグレードできる
  - これらのレコードはAレコードやAAAAレコードと一緒に問い合わせることができ、
    更新されたアルゴリズムは接続確立を改善するためにSVCB応答をどう扱うかを定義する

## 2. Conventions and Definitions
変更なし

## 3. Overview
- 本書は、Happy Eyeballs Connection Setupと呼ぶ接続確立方式を定義する。この方式には、次のいくつかの段階がある
  - 1. ホスト名を宛先エンドポイントへ非同期に名前解決する (4. Hostname Resolution)
  - 2. 名前解決された宛先エンドポイントを並べ替える (5. Grouping and Sorting Endpoints)
  - 3. 非同期の接続試行を開始する (6. Connection Attempts)
  - 4. 1つの接続を正常に確立し、その他の試行をキャンセルする (6. Connection Attempts)
- 本書は、宛先アドレスファミリの優先ポリシーがIPv4よりIPv6を優先することを前提とする
  - IPv6にはIPv4を改善するために設計された多くの望ましい特性がある [IPV6]
- 本書は、優先ポリシーがTCPよりQUICを優先することを前提とする
  - QUICは、セキュアな接続を確立するのに1パケットのみを必要とし、TCPと比べて高速 [QUIC]
-  ホストが異なる優先設定になっている場合でも本書の推奨事項は容易に適応できる

## 4. Hostname Resolution
- クライアントが名前のあるホストへ接続を確立しようとする際、
  接続を確立するために使用できる宛先エンドポイントを特定する必要がある
- クライアントはDNS問い合わせを送信して応答を収集することにより、エンドポイントを名前解決する
- 本節では、クライアントがDNS問い合わせをどのように開始し、その応答を非同期にどのように処理するかを説明する

### 4.1 Sending DNS Queries
- クライアントはまず、名前のあるホストへの問い合わせにどのDNSリソースレコードを含めるかを決定する必要がある
  - この決定は、クライアントが現在のProvisioning Domain (PvD) [PvD] において、
    IPv4および/またはIPv6を使った接続性を持っているかに基づく
    - 一般にあるアドレスファミリの接続性は以下のように定義される
      - パケットの送信元として、そのアドレスファミリのループバック [RFC3927] 以外のアドレスが1つ以上ある
      - かつパケットの送信元として、そのアドレスファミリのリンクローカル [RFC4291] 以外のアドレスが1つ以上ある
      - かつそのアドレスファミリのリンクローカルでないルートが少なくとも1つある
- [MUST] IPv6の接続性がある場合、クライアントはAAAAレコードの問い合わせを含めなければならない
- [MUST] IPv4の接続性がある場合、クライアントはAレコードの問い合わせを含めなければならない
- [MUST] IPv4の接続性がなくてもクライアントがネットワーク上でNAT64 prefix [NAT64] を検出している場合、
  クライアントはAレコードの問い合わせを含めなければならない
  - NAT64 prefixの検出と応答の扱いの詳細は 8. Handling NAT64 Networks を参照
- AAAAレコードとAレコードの問い合わせに加えて、接続を確立するアプリケーションに応じて
  クライアントはSVCBレコードまたはHTTPSレコード [SVCB] を問い合わせることができる
  - [SHOULD] HTTPまたはHTTPSを使用するアプリケーション(WebSocketsを使用するアプリケーションを含む) では、
    クライアントはHTTPSレコードの問い合わせを送信するべき
- [SHOULD] すべてのDNS問い合わせは、可能な限り連続して行うべき
  - [SHOULD] 問い合わせを送信する順序は、次のとおりとするべきである (該当しない問い合わせは省く)
    - 1. SVCBまたはHTTPSの問い合わせ
    - 2. AAAAの問い合わせ
    - 3. Aの問い合わせ
  - この順序は、Happy Eyeballsアルゴリズムを実装するクライアントが
    送信される問い合わせに具体的に影響を与えられるか、
    問い合わせの送信方法についてDNSスタブリゾルバから保証を得ていることを前提としている
    - これは利用可能なAPIによっては、すべての環境やオペレーティングシステムで可能なわけではない
- なお、DNSスタブリゾルバの実装自体がHappy Eyeballsアルゴリズムを採用している場合がある
  - 暗号化DNSサーバ (e.g. [DOT]、[DOH]、[DOQ] を使用し、[RFC9461] によって発見される場合がある) に接続する場合など
    - [RFC10001] 4.3はスタブリゾルバがデュアルスタック環境をどのように扱うべきかについての指針を示している
  - この指針に従うことはHappy Eyeballsを実装するクライアントにとって有益である
  - DNS名前解決の間、デュアルスタックネットワークが適切に扱われることが保証されるためであり、
    DNS名前解決は、Happy Eyeballsアルゴリズムの残りの部分がうまく機能するための前提条件であるため

### 4.2 Handling DNS Answers Asynchronously
- クライアントはDNS問い合わせに対する十分な応答を受け取ると、
  エンドポイントの並べ替え (5. Grouping and Sorting Endpoints) と接続確立 (6. Connection Attempts) の段階へ
  進むことができる
- [SHOULD NOT] 実装は接続確立の次の手順を開始する前にすべてのDNS応答が返ってくるのを待つべきではない
  - ある問い合わせが失敗したり返ってくるまでに時間がかかる場合、
    その応答を待つことによって、すでに受信した応答で進められるはずの接続確立が大幅に遅れる可能性がある
  - [SHOULD] したがってクライアントはDNS名前解決を非同期として扱い、異なるレコードタイプを独立して処理するべき
    - プラットフォームが非同期DNS APIを提供していない場合、
      レコードタイプごとに個別の同期問い合わせを並列に実行することでこの動作を模倣できる
- クライアントは、次の条件セットのいずれかが満たされた時点で、エンドポイントの並べ替えと接続確立へ進む
  - 何らかの肯定的な (空でない) アドレス応答を受信している
    - かつ、問い合わせた優先アドレスファミリについて、肯定的 (空でない) または否定的な (空の) 応答を受信している
    - かつ、SVCB/HTTPSのサービス情報を受信している (または否定的な応答を受信している)
  - または何らかの肯定的な (空でない) アドレス応答を受信ている
    - かつ名前解決の待機時間が経過し、他の応答が届いていない
  - すべての応答が否定的な応答で返ってきた場合、接続確立は失敗するか、他の応答を受信するまで待つ必要がある

```text
肯定的な応答 ... AAAAまたはAレコードで受信したIPアドレス、またはSVCB/HTTPSレコードで直接受信したIPアドレスヒント

否定的な応答 ... IPアドレスを含まないAAAAまたはAレコードへの応答
(NXDOMAINのようなエラーを伴う場合も伴わない場合も含む)

```

- IPv6とIPv4の両方にデフォルトルートがあるネットワークでは、
  IPv6が優先アドレスファミリであると想定される
- IPv6とIPv4のどちらか一方にだけデフォルトルートがある場合は、
  そのアドレスファミリをアルゴリズムを進めるうえでの優先アドレスファミリとみなす
- 優先アドレス (AAAAレコード経由) をサービス情報 (SVCB/HTTPSレコード経由) とあわせて受信する機会を与える短い時間を
  名前解決の待機時間 = Resolution Delayとする
  - AAAAまたはSVCB/HTTPSレコードがAレコードより数ミリ秒遅れて届く場合を考慮したもの
  - Resolution Delayの推奨値は25ms

#### 4.2.1. Resolving SVCB/HTTPS Aliases and Targets
- SVCBレコードとHTTPSレコードはネットワークサービスに関する情報を記述する
  - 個々のレコードは、AliasModeまたはServiceModeのいずれか
    - AliasModeでは、別名に対する追加のSVCB/HTTPS問い合わせが必要
    - ServiceModeレコードは、問い合わせ対象の元の名前に関連付けられている場合 (この場合TargetNameは`.`) と、
      別のサービス名に関連付けられている場合 ([SVCB] 2.5) がある
- 本書のアルゴリズムは、ServiceModeレコードが利用可能になるまで、サービス情報を受信したとはみなさない
- ServiceModeレコードは、ipv6hintおよびipv4hintパラメータにより、IPアドレスヒントを含むことができる
  - [SHOULD] これらを受信した場合、TargetNameに対応するAレコードとAAAAレコードがまだ利用できないときは、
    アルゴリズム上、肯定的で空でない応答とみなすべき
    - クライアントは、それらのTargetNameに対するレコードをまだ受信していない場合、
      依然としてAおよびAAAAの問い合わせを発行する必要がある
      - それらのレコードを受信したときは、ヒントを置き換え、利用可能な応答の集合を新しい応答として更新する (4.3)

### 4.3. Handling New Answers
- 接続試行が進行中で、まだ接続が1つも確立されていない間に新しいレコードが届いた場合、新しく受信したエンドポイントは
  利用可能な候補エンドポイントのリストに組み込まれ (7. DNS Answer Changes During Happy Eyeballs Connection Setup) 、
  接続が1つ確立されるまで新しいエンドポイントを含めて接続試行の処理を続ける

### 4.4. Handling Expired Answers
- 以前に受信したDNS応答は、接続試行が進行中の間に有効期限切れ (TTLの超過) になることがある
- Happy Eyeballsクライアントは応答の有効期限が切れても、進行中のそれらの試行をキャンセルしない
  - [MAY] ただし、元の応答がまだ接続の成功につながっていない場合に限り、
    クライアントは元のレコードの有効期限が切れたあとに、期限切れでない応答を取得するため
    新しいDNS問い合わせを発行してもよい
    - 新しい応答の追加は、4.3 および 7. DNS Answer Changes During Happy Eyeballs Connection Setup のとおりに扱われる
    - つまり、進行中の接続試行はキャンセルされないが接続試行がまだ開始されておらず、
      かつ解決済みエンドポイントのリストにもう存在しないエンドポイントは削除される
- Happy Eyeballsにより、クライアントが解決済みエンドポイントのリストへの更新を非同期に扱えることによって、
  期限切れでない応答を待つ間、期限切れの応答を楽観的 (optimistically) に使うことが可能になる
  - この方式はoptimistic DNSと呼ばれ、[OPTIMISTIC-DNS] で説明されている

## 5. Grouping and Sorting Endpoints
- 名前解決された宛先エンドポイントのいずれかに接続を試みる前に、クライアントは試行を開始する順序を定める
  - 順序が定まると、クライアントは短い遅延のあとに各選択肢を競争させる単純なアルゴリズムを使うことができる
    (6. Connection Attempts)
  - 順序付きリストには、この時点までに受信した両方のアドレスファミリのすべてのエンドポイントと
    すべてのプロトコルを含めることが重要
    - これによりクライアントは、最初のIPv4アドレスと最初のIPv6アドレスだけでなく、
      リスト全体についてHappy Eyeballsの競争効果を得られる
- クライアントは受信したDNS応答に基づいてエンドポイントを3段階でグループ化し、並べ替える
  - 後続の各段階の並べ替えは、それ以前に定義されたグループの中での順序と優先度だけを変更する

```text
1. アプリケーションプロトコルとセキュリティ要件によるグループ化と並べ替え (5.1)
2. サービスの優先度によるグループ化と並べ替え (5.2)
3. 宛先エンドポイントの優先設定による並べ替え (5.3)
```

### 5.1. Grouping By Application Protocols and Security Requirements
- クライアントはまず、宛先エンドポイントがどのアプリケーションプロトコルをサポートし、
  それらのエンドポイントがどのセキュリティ機能を提供しているかに基づいてグループ化する
  - これらはSVCB/HTTPSレコードに含まれる、アプリケーション層プロトコルに関する情報 ("alpn"値) や
    TLS Encrypted Client Hello の設定 ("ech"値 [SVCB-ECH]) など他のパラメータに基づく
- 応答にSVCB/HTTPSの情報がまったく含まれない場合やすべての応答が同じSVCB/HTTPSレコードに関連付けられている場合は
  すべての応答が1つのグループに属しており、
  クライアントはそれらが同じプロトコルとセキュリティ特性をサポートしているとみなす
  - 一方クライアントは複数の異なるSVCB/HTTPSレコードを受信した時点で、
    異なる機能を広告している、異なる宛先エンドポイントの集合があることを認識する
    - [SHOULD] クライアントはこれらのエンドポイントを別々のグループに分けるべき
      - グループ内のすべてのエンドポイントが、同じアプリケーションプロトコルと関連する
        セキュリティ特性を共有するようにするため
        - クライアントにとって何のパラメータが関連するかは、クライアントの実装とアプリケーションに依存する。

この段階では、一部の宛先エンドポイントを複数のグループに追加する必要がある場合があることに注意する

```text
e.g.
example.com. 60 IN HTTPS 1 svc1.example.com. ( alpn="h3,h2" ipv6hint=2001:db8::2 )
example.com. 60 IN HTTPS 1 svc2.example.com. ( alpn="h2" ipv6hint=2001:db8::4 )

この場合2001:db8::2はHTTP/3とHTTP/2の両方で使用でき、2001:db8::4はHTTP/2のみ使用できる。
クライアントがHTTP/3に対応するエンドポイントとHTTP/2に対応するエンドポイントでグループを作る場合、
2001:db8::2は両方のグループに存在することになる (他のセキュリティ特性がすべて同じと仮定した場合)
```

- 6. Connection Attempts で説明する接続の競争はこれらのグループのいずれか1つの中にある、
  異なる宛先エンドポイントの選択肢に対して適用される
  - 異なるセキュリティ特性やプロトコル特性を持つエンドポイントのグループ間で優先順位を付けたり、
    フォールバックしたりするロジックは、実装定義である

#### 5.1.1. When to Apply Application Preferences
- 特定のアプリケーションプロトコルやセキュリティ機能を別々にグループ化するかどうかは、
  クライアントアプリケーションの実装判断とする
  - [SHOULD] クライアントはアプリケーションプロトコルや機能の使用が重要でない場合、
    別々にグループ化して並べ替えることを避けるべきである
    - 単純なウェブページを読み込むHTTPクライアントの場合、
      HTTP/3とHTTP/2のどちらを使っても大きな違いを感じないため、ALPNをまとめてグループ化し、
      HTTP/3の優先順位がHTTP/2より後ろになりうる、サービス側が決めた優先順位を尊重できる
    - 自身のアプリケーションのユースケースで、HTTP/3の信頼性のないフレームを送信する機能を使うことで、
      大きな性能向上を得られるようなクライアントの場合はHTTP/3をHTTP/2の前にグループ化する
    - プライバシーに敏感なトラフィックについてTLS ECHの使用を必須とするか強く優先するクライアントもあれば、
      ECHを機会主義的にサポートするアプリケーションもある
      - [SVCB-ECH] 8は、ECH設定を含む応答と含まない応答が混在するSVCBレコードセットを推奨しないとしているが、
        そのようなケースがありうることにも触れている
        - サービスが、ECH設定を含まない応答より優先順位の低いSVCB応答にだけ、ECH設定を含める可能性がある
          - これは実験やロールアウトの戦略として使われることがある
          - このようなケースがあるため、クライアントはECH情報を使わない場合や、
            接続がECHの使用で利益を得られない場合には、ECHを含む応答を恣意的にグループ化して先頭に並べるべきではない
            - [MAY] アプリケーションがECHを優先する理由がある場合、クライアントはそれらの応答を
              別にグループ化して優先してもよい
              - これは公開されたサービスレコードの優先順位と衝突する可能性があるが、
                サービスが公開した応答はすべてクライアントが使用する資格があり、
                クライアントはそれらを使うことを選べる

### 5.2. Grouping By Service Priority
- 次に、(SVCB/HTTPSレコードで定義される) 異なるサービスをまたいでグループ化し、これらのグループを優先度で並べ替える
  - この手順により、サーバが公開した優先度を、クライアントの接続確立アルゴリズムに反映できる
- SVCB [SVCB] レコードは、ServiceModeの各応答に優先度を示す
  - この優先度は、レコード自体に含まれるIPv4またはIPv6のアドレスヒントと、
    ServiceModeレコード内の名前に対するAまたはAAAAの問い合わせで受信したアドレスのすべてに適用される
    - SVCBServiceModeレコードの優先度は、常に0より大きい。
  - 数値が最も小さい (1など) SVCB応答が先に並べられ、数値がより大きい応答は後に並べられる
  - TargetNameが`.`のSVCBレコードは、そのレコード内のowner名に適用される
    - そのSVCBレコードの優先度は、同じオーナー名のAまたはAAAAレコードのすべてに適用される
    - これらの応答は、そのSVCBレコードの優先度に従って並べ替えられる
- [SHOULD] 特定のSVCBサービスから (5.1 で定義されるグループの中で) 関連付けられたAAAAまたはAレコード
  もしくはアドレスヒントのいずれかによって受信したエンドポイントはすべて、
  クライアントによって1つのグループに分けられるべき
  - [SHOULD] これらのサービスに基づくグループは、そのうえでサービスの優先度を使って並べ替えられるべき
- 応答にSVCB/HTTPSの情報がまったく含まれない場合、
  またはすべての応答が同じSVCB/HTTPSレコードに関連付けられている場合、
  すべての応答は、同じ優先度を持つ1つのグループに属する
- [SHOULD] 応答に複数のサービスがあり、したがって同じ優先度を持つ複数のグループがある場合、
  クライアントは、これらのグループをランダムにシャッフルするべき
- [SHOULD] 受信したSVCB/HTTPSサービスがあるものの関連付けられたサービスを持たないAAAAまたはAレコードがある場合
  (e.g. `.`のTargetNameを使った元の名前に対するSVCB/HTTPSレコードを受信しなかった場合)、
  関連付けられていないアドレスは、リストの末尾で優先されるエンドポイントのグループに入れられるべき

### 5.3. Sorting Destination Endpoints Within Groups
- エンドポイントのグループそれぞれの中で5.1と5.2のロジックに基づくグループ化を行ったあと、
  クライアントは優先設定と履歴データに基づいてエンドポイントを並べ替える
- [MUST] まずクライアントは、宛先アドレス選択 ([RFC6724]  6) を使ってエンドポイントを並べ替えなければならない
  - [SHOULD] クライアントがステートフルであり、
    かつ各エンドポイントのIPアドレスへアクセスする経路について想定される往復時間 (RTT) の履歴を持っている場合、
    ルール8とルール9の間に、RTTが低いアドレスを優先する宛先アドレス選択のルールを追加するべき
    - [SHOULD] さらにクライアントが過去に使用したアドレスを記録している場合、
      RTTルールとルール9の間に、使用済みアドレスを未使用のアドレスより優先する宛先アドレス選択のルールを追加するべき
      - これは認証の際にクライアントのIPアドレスを使うサーバに役立つ
        - TCP Fast Open [RFC7413] や、一部のHypertext Transport Protocol (HTTP) Cookieがその例である
        - [MUST / MUST NOT] この履歴データは、当該エンドポイント固有のプライバシーに敏感な情報に使われるのと
          同じ境界で分割しなければならず、異なるProvisioning Domain (PvD) [PvD] の間で使用してはならない
          - 複数のPvDの扱いに関する議論は9. Handling Multiple Networks and Network Changesにある
        - [MUST] 履歴データを使用する実装は、異なる履歴データを持つクライアントが
          最終的には同じ挙動に収束することを保証しなければならない
          - たとえばクライアントは、新しいアドレスが試行されるよう、定期的に履歴データを無視できる
- [SHOULD] 次にクライアントは、アドレスファミリが交互になるよう、順序付きリストを修正するべき
  - リストの先頭にあるアドレスファミリの次には、もう一方のアドレスファミリのエンドポイントが続くべき
    - たとえば、並べ替え後のリストの先頭のエンドポイントがIPv6アドレスを持つ場合、
      最初のIPv4エンドポイントをリストの2番目になるよう繰り上げるべき
      - [MAY] 実装は一方のアドレスファミリを、次を試す前にそのファミリの複数のアドレスを試行することで、
        より優先することを選んでもよい
        - 最初のアドレスファミリのエンドポイントが連続する数はPreferred Address Family Countと呼ばれ、
          設定可能な値にできる
          - これにより、あるアドレスファミリでの接続性が損なわれている場合に、
            そのアドレスファミリのエンドポイントの長いリストを待ち続けることを避けられる
- 本節で説明するエンドポイントの選択は、宛先アドレスにのみ適用される
  - 送信元アドレス選択 ([RFC6724-UPDATE] 3.2) は、宛先アドレスごとに1回行われ、本書の範囲外である。

## 6. Connection Attempts
- ここまでに受信したエンドポイントのリストが構築されたら、クライアントは接続を試みる
  - [SHOULD NOT] 不当なネットワーク負荷を避けるため、接続試行は同時に行うべきではない
    - 代わりに、まず単一のエンドポイントへの接続試行を1つ開始し、他のものはそのあとに1つずつ開始する
    - 複数の接続試行が並行して行われることがあるため、新しい接続試行の開始は以前の試行に影響を与えない
    - [SHOULD] 接続試行のいずれかが成功したら (6.1)、まだ成功していない他のすべての接続試行はキャンセルされるべき
      - [SHOULD] 接続としてまだ試行されていないエンドポイントは無視されるべきである
  　    - [MAY] このとき新しいエンドポイントは接続には使用されないため、非同期のDNS問い合わせはキャンセルしてもよい
          - [SHOULD] ただしDNSクライアントリゾルバはDNSキャッシュに格納されて後続の接続で使用できるため、
            ネットワークからのDNS応答を、短い期間 (1s推奨) は引き続き処理するべき
- [New] 接続が成功した時点で残っている進行中の試行をキャンセルすることによって、
  ネットワークとサーバへの不要な負荷を避ける
  - より優先された先の試行 (QUICやIPv6など) があとのフォールバックの試行 (TCP上のTLSやIPv4など) が成功する前に
    完了しなかった場合、その経路ではパケットロス、レート制限、その他の障害が起きている可能性があり、
    そちらに切り替えることで性能が低下しうる
    - [MAY] ただしより多くの文脈を持つクライアント実装は、すでに進行中の優先された試行をすぐにキャンセルせず、
      バックグラウンドで継続させてもよい (e.g. 後続のリクエストでHTTP/2よりHTTP/3を優先するHTTP接続マネージャ)
      - その際はその接続を優先する前に経路の品質を評価し、不要になった冗長な接続を閉じるよう注意する
      - 接続プールの管理や、確立済みの接続間の切り替えの具体的な仕組みは、本書の範囲外である
      - (shioimm)
        - 1. 優先度の高いQUIC (HTTP/3) の試行が、遅れていてまだ完了していない
        - 2. 先にフォールバックのTCP (HTTP/2) が成功する
        - 3. Happy Eyeballsの原則では、まだ成功していないQUICの試行はキャンセルされる
          - ただしこの先も同じホストに何度もリクエストを送ることが確定している場合、
            少し待てばQUICで接続できるかもしれないような状況において、
            HTTP接続マネージャはQUICの試行を捨てずにバックグラウンドで続けさせ、
            完了したら以後のリクエストをHTTP/3に切り替える、という判断ができる
- [New] 各接続試行は、それぞれ独自のコネクション識別子と暗号ハンドシェイクの状態を持つ独立したトランスポート接続
  (e.g. 別々のTCP接続や別々のQUIC接続) であるため、ハンドシェイクのパケットは試行間で再利用できない
  - [MUST NOT] TLSを使用する場合 (TCP上であれQUICの一部であれ)、
    クライアントは接続試行間で鍵共有 (key share) を再利用してはならない ([RFC9846] 4.2.8)
    - [MUST NOT] 同様に、複数のQUIC接続を試行する場合 (IPv6とIPv4など)、
      クライアントは同じQUIC Initialパケットのコピーを送信したり、
      試行間でConnection IDを再利用したりしてはならない ([QUIC] 9.5)
      - Connection IDと暗号ハンドシェイクの値の再利用を避けることで、
      - 観測者がネットワーク経路をまたいでクライアントのアドレスを関連付けることを防げる
      - 試行はConnection Attempt Delayで隔てられるため、ほとんどの接続は追加のハンドシェイクのコストを負わずに、
        最初の試行で完了する
- [SHOULD] アプリケーションやセキュリティ要件によるエンドポイントのグループ化 (5.1) で複数のグループができた場合、
  アプリケーションは、最も優先される選択肢への接続試行から始めるべきである
  - 最も優先されるグループの外にあるエンドポイントを試行する方針はクライアント実装に委ねられ、本書の範囲外
- [SHOULD] サービスによるエンドポイントのグループ化 (5.2) で複数のグループができた場合、
  最初のグループのすべてのエンドポイントを開始してから、次のグループを使った試行を開始するべき
- [SHOULD] サービスグループをまたぐ試行は、並行して継続できるようにするべき
  - 事実上、グループは1つのリストに平坦化される
  - これらのグループの意図は、最も優先されるサービスを厳密に優先すること
    - したがって、優先度の高いグループに多くのエンドポイントがある場合、
      優先度の低いグループへフォールバックするまでに、長い遅延が生じる可能性がある
- 単純な実装は、次の接続試行を開始するまでの待ち時間として、固定の遅延を持てる
  - この遅延はConnection Attempt Delayと呼ばれ、デフォルトの遅延の推奨値の1つは250ms
    - より細やかな実装の遅延は、再送タイマ ([RFC6298]、[RFC9002]) に基づき、
    - 前回の試行がハンドシェイクを再試行する時点 (2つ目のTCP SYNや2つ目のQUIC Initialの送信など) に対応させるべき
      - クライアントが、同じホストまたはプレフィックスへの他の接続から収集した過去のRTTデータを持っている場合、
        この情報を遅延に反映させることができる
        - トランスポートの再送タイマは、一般にほとんどの正常な接続が再送なしで最初のハンドシェイクを完了するように、
          調整されている
          - 最初のハンドシェイクの再送の時点あたりまで待つことで、一般的なケースでは冗長な接続試行を開始せずに、
            優先された試行に成功する妥当な機会を与えられる
            - 一方で、最初のパケット (またはその応答) が失われた可能性が高くなった時点で、
              すぐに次の試行を開始できる。
              - このアルゴリズムは最初のハンドシェイクパケットの再送の時刻を近似することだけを試みるべきであり、
                指数的なタイマのバックオフに影響されうる、それ以降の再送は対象としないことに注意する
                - 実際にはHappy Eyeballsを実装する層は、トランスポート層より上で動作することが多く、
                  トランスポート層の再送の正確なタイミングを直接制御できない、または知らない場合がある
                  - 再送のタイミングがわかっている、または近く推定できる場合でも、
                    以前の試行でのハンドシェイクの再送を、新しい試行の最初のパケットと同時に送ると、
                    ネットワークがすでにパケットロスを経験しているときに、小さなパケットのバーストを引き起こしうる
                    - [MAY] 実装は両方のパケットを同時に送信しないよう、小さなジッタやペーシングを適用してもよい
- [SHOULD] セッション再開の仕組み (TLSセッションチケット [RFC8446] やQUIC 0-RTT [RFC9001] など) を
  サポートするクライアントは、再開した接続にも、新規の接続と同じConnection Attempt Delayを使うべき
- [MUST] Connection Attempt Delayには、特に過去のデータを使って計算する場合、下限がなければならない
  - [MUST NOT] 具体的には、後続の接続は前回の試行から10ms以内に開始してはならない
    - 推奨される最小値は100ms (Minimum Connection Attempt Delay)
      - この最小値は高いパケットロス率のもとで輻輳崩壊を避けるために必要
- [SHOULD] Connection Attempt Delayには上限もあるべきで (Maximum Connection Attempt Delay)
  - 現在の推奨値は2s
- [New] [MAY] 実装は、先行する試行がまだ進行中のうちに開始する追加の接続試行ごとに、
  遅延に固定の係数 (Connection Attempt Delay Multiplier) を掛けることで、Connection Attempt Delayを増やしてもよい
  - この倍率は実装が使う基準の遅延 (RTTデータがあれば上で説明したRTT由来の推定値、なければ固定のデフォルト値) に
    適用される
  - 短い基準遅延は最初のフォールバックをすばやく開始し、倍率は後続の試行の間隔を広げて、全体の試行頻度を低く保つ
    - e.g. 固定の基準遅延が50msで倍率が2の場合、試行は0、50、150、350、750msに開始される
    - 倍率が1なら、遅延は一定のまま
    - [MAY] 推奨されるMinimum Connection Attempt Delayより小さい基準遅延を使ってもよい (1より大きい倍率とともに)
      - ただし、10msという絶対的な下限は引き続き適用される
- Connection Attempt Delayは、Next Connection Attempt Timerと呼ばれるタイマの設定に使われる
  - このタイマが発火し、接続がまだ正常に確立されていなければ、次の接続試行が開始され、
    タイマは新しい遅延値にリセットされるか、リストの終端に達した場合はキャンセルされる
    - 遅延値は、接続試行ごとに異なりうることに注意する (使用するプロトコルと推定RTTによる)
- [New] 本書のアルゴリズムは単一の接続の確立を記述しており、Connection Attempt Delayは
  単一のHappy Eyeballs手続きの試行頻度を制限する
  - しかし、アプリケーションは、短期間のうちに、同じホストやサービスへ複数の同時接続リクエストを開始することがある
    - (e.g. 並列のHTTP/1.1リクエストや、投機的なpreconnectの直後に実際のリクエストが続く場合)
    - 調整なしにHappy Eyeballsの手続きを並行して実行すると、同じ宛先への接続試行の全体のバーストが生じうる
    - 複数の接続のプールを管理する仕組みは本書の範囲外だが、
      クライアント実装は1つの接続を共有できる場合 (HTTP/2やHTTP/3など) には、
      名前解決と進行中の接続確立をまとめることで、
      複数の接続が必要な場合には同じホストやサービスを対象とする、並行するHappy Eyeballs手続きの間で
      試行のペーシングを調整することで、こうしたバーストを緩和できる
