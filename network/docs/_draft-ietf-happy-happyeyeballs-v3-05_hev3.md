# Happy Eyeballs Version 3: Better Connectivity Using Concurrency
https://datatracker.ietf.org/doc/draft-ietf-happy-happyeyeballs-v3/

## 1. Introduction
- 現代のインターネット上で動作する多くの通信プロトコルは、ホスト名を使用する
- ホスト名は多くの場合、複数のIPアドレスに名前解決され、それぞれが異なる性能や接続特性を持つ可能性がある
- 特定のアドレスやアドレスファミリ (IPv4またはIPv6) はネットワーク上で遮断されていたり、
  破損していたり、最適でなかったりする可能性がある
  - そのため、複数の接続を並行して試行するクライアントは、より迅速に接続を確立できる可能性がある
- 本書は、デュアルスタックホストでユーザが認識する遅延を低減する技術であるHappy Eyeballsのアルゴリズムを定義する
  - この定義は [HEV2] の記述を更新するものであり、[HEV2] 自体が [RFC6555] を置き換えたものである
- 名前解決されたエンドポイントに対して接続を競争させるHappy Eyeballsアルゴリズムは、
  ユーザへの遅延を可能な限り避けるために、いくつかの段階を持つ
  - その際IPv6の使用を優先することや、
    HTTP/3 [HTTP3] やTLS Encrypted Client Hello [ECH] といったプロトコルが利用可能であることなど、
    クライアントの優先事項を尊重する
- 本書では、接続を開始するときにDNS問い合わせをどのように開始するか、
  DNS応答で受け取った宛先アドレスのリストをどのように並べ替えるか、
  そして接続試行をどのように競争させるかについて論じる
- 本書で定義するアルゴリズムと [HEV2] の主な違いは、
  SVCB / HTTPSリソースレコード [SVCB] への対応が追加されたことである
  - SVCBレコードは、代替エンドポイント、アプリケーションプロトコルの対応状況、Encrypted Client Hello [ECH] の鍵、
    アドレスヒント、およびアクセス対象のサービスに関するその他の関連情報を提供する
  - HTTP/3 over QUIC [HTTP3] のようなプロトコルの対応状況を名前解決中に検出することで、
    HTTP Alternative Services [AltSvc] などの他の検出メカニズムの情報を使って後続の試行を行うのを待つのではなく、
    現在の接続試行の中でプロトコルをアップグレードできる
  - これらのレコードはAレコードやAAAAレコードと一緒に問い合わせることができ、
    更新されたアルゴリズムは接続確立を改善するためにSVCB応答をどう扱うかを定義する

## 3. Overview
- 本書は、Happy Eyeballs Connection Setupと呼ぶ接続確立方式を定義する。この方式には、次のいくつかの段階がある
  - 1. ホスト名を宛先エンドポイントへ非同期に名前解決する (4. Hostname Resolution)
  - 2. 名前解決された宛先エンドポイントを並べ替える (5. Grouping and Sorting Addresses)
  - 3. 非同期の接続試行を開始する (6. Connection Attempts)
  - 4. 1つの接続を正常に確立し、その他の試行をキャンセルする (6. Connection Attempts)
- 本書は、宛先アドレスファミリの優先ポリシーがIPv4よりIPv6を優先することを前提とする
  - IPv6にはIPv4を改善するために設計された多くの望ましい特性がある [IPV6]
- 本書は、優先ポリシーがTCPよりQUICを優先することを前提とする
  - QUICは、セキュアな接続を確立するのに1パケットのみを必要とし、TCPと比べて高速 [QUIC]
-  ホストが異なる優先設定になっている場合でも本書の推奨事項は容易に適応できる

## 4. Hostname Resolution
- クライアントが名前のあるホストへ接続を確立しようとする際、
  接続を確立するために使用できる宛先エンドポイントを特定する必要がある
- クライアントはDNS問い合わせを送信して応答を収集することにより、エンドポイントを名前解決する
- 本節では、クライアントがDNS問い合わせをどのように開始し、その応答を非同期にどのように処理するかを説明する

### 4.1 Sending DNS Queries
- クライアントはまず、名前のあるホストへの問い合わせにどのDNSリソースレコードを含めるかを決定する必要がある
  - この決定は、クライアントが現在のProvisioning Domain (PvD) [PvD] において、
    IPv4および/またはIPv6を使った接続性を持っているかに基づく
    - 一般にあるアドレスファミリの接続性は以下のように定義される
      - パケットの送信元として、そのアドレスファミリのループバック [RFC3927] 以外のアドレスが1つ以上ある
      - かつパケットの送信元として、そのアドレスファミリのリンクローカル [RFC4291] 以外のアドレスが1つ以上ある
      - かつそのアドレスファミリのリンクローカルでないルートが少なくとも1つある
- [MUST] IPv6の接続性がある場合、クライアントはAAAAレコードの問い合わせを含めなければならない
- [MUST] IPv4の接続性がある場合、クライアントはAレコードの問い合わせを含めなければならない
- [MUST] IPv4の接続性がなくてもクライアントがネットワーク上でNAT64 prefix [NAT64] を検出している場合、
  クライアントはAレコードの問い合わせを含めなければならない
  - NAT64 prefixの検出と応答の扱いの詳細は 8. Handling NAT64 Networks を参照
- AAAAレコードとAレコードの問い合わせに加えて、接続を確立するアプリケーションに応じて
  クライアントはSVCBレコードまたはHTTPSレコード [SVCB] を問い合わせることができる
  - [SHOULD] HTTPまたはHTTPSを使用するアプリケーション(WebSocketsを使用するアプリケーションを含む) では、
    クライアントはHTTPSレコードの問い合わせを送信するべき
- [SHOULD] すべてのDNS問い合わせは、可能な限り連続して行うべき
  - [SHOULD] 問い合わせを送信する順序は、次のとおりとするべきである (該当しない問い合わせは省く)
    - 1. SVCBまたはHTTPSの問い合わせ
    - 2. AAAAの問い合わせ
    - 3. Aの問い合わせ
  - この順序は、Happy Eyeballsアルゴリズムを実装するクライアントが
    送信される問い合わせに具体的に影響を与えられるか、
    問い合わせの送信方法についてDNSスタブリゾルバから保証を得ていることを前提としている
    - これは利用可能なAPIによっては、すべての環境やオペレーティングシステムで可能なわけではない
- なお、DNSスタブリゾルバの実装自体がHappy Eyeballsアルゴリズムを採用している場合がある
  - 暗号化DNSサーバ (e.g. [DOT]、[DOH]、[DOQ] を使用し、[RFC9461] によって発見される場合がある) に接続する場合など
    - [RFC10001] 4.3はスタブリゾルバがデュアルスタック環境をどのように扱うべきかについての指針を示している
  - この指針に従うことはHappy Eyeballsを実装するクライアントにとって有益である
  - DNS名前解決の間、デュアルスタックネットワークが適切に扱われることが保証されるためであり、
    DNS名前解決は、Happy Eyeballsアルゴリズムの残りの部分がうまく機能するための前提条件であるため

### 4.2 Handling DNS Answers Asynchronously
- クライアントはDNS問い合わせに対する十分な応答を受け取ると、
  エンドポイントの並べ替え (5. Grouping and Sorting Addresses) と接続確立 (6. Connection Attempts) の段階へ
  進むことができる
- [SHOULD NOT] 実装は接続確立の次の手順を開始する前にすべてのDNS応答が返ってくるのを待つべきではない
  - ある問い合わせが失敗したり返ってくるまでに時間がかかる場合、
    その応答を待つことによって、すでに受信した応答で進められるはずの接続確立が大幅に遅れる可能性がある
  - [SHOULD] したがってクライアントはDNS名前解決を非同期として扱い、異なるレコードタイプを独立して処理するべき
    - プラットフォームが非同期DNS APIを提供していない場合、
      レコードタイプごとに個別の同期問い合わせを並列に実行することでこの動作を模倣できる
- クライアントは、次の条件セットのいずれかが満たされた時点で、エンドポイントの並べ替えと接続確立へ進む
  - 何らかの肯定的な (空でない) アドレス応答を受信している
    - かつ、問い合わせた優先アドレスファミリについて、肯定的 (空でない) または否定的な (空の) 応答を受信している
    - かつ、SVCB/HTTPSのサービス情報を受信している (または否定的な応答を受信している)
  - または何らかの肯定的な (空でない) アドレス応答を受信ている
    - かつ名前解決の待機時間が経過し、他の応答が届いていない
  - すべての応答が否定的な応答で返ってきた場合、接続確立は失敗するか、他の応答を受信するまで待つ必要がある

```
肯定的な応答 ... AAAAまたはAレコードで受信したIPアドレス、またはSVCB/HTTPSレコードで直接受信したIPアドレスヒント

否定的な応答 ... IPアドレスを含まないAAAAまたはAレコードへの応答
(NXDOMAINのようなエラーを伴う場合も伴わない場合も含む)

```

- IPv6とIPv4の両方にデフォルトルートがあるネットワークでは、
  IPv6が優先アドレスファミリであると想定される
- IPv6とIPv4のどちらか一方にだけデフォルトルートがある場合は、
  そのアドレスファミリをアルゴリズムを進めるうえでの優先アドレスファミリとみなす
- 優先アドレス (AAAAレコード経由) をサービス情報 (SVCB/HTTPSレコード経由) とあわせて受信する機会を与える短い時間を
  名前解決の待機時間 = Resolution Delayとする
  - AAAAまたはSVCB/HTTPSレコードがAレコードより数ミリ秒遅れて届く場合を考慮したもの
  - Resolution Delayの推奨値は25ms

#### 4.2.1. Resolving SVCB/HTTPS Aliases and Targets
- SVCBレコードとHTTPSレコードはネットワークサービスに関する情報を記述する
  - 個々のレコードは、AliasModeまたはServiceModeのいずれか
    - AliasModeでは、別名に対する追加のSVCB/HTTPS問い合わせが必要
    - ServiceModeレコードは、問い合わせ対象の元の名前に関連付けられている場合 (この場合TargetNameは`.`) と、
      別のサービス名に関連付けられている場合 ([SVCB] 2.5) がある
- 本書のアルゴリズムは、ServiceModeレコードが利用可能になるまで、サービス情報を受信したとはみなさない
- ServiceModeレコードは、ipv6hintおよびipv4hintパラメータにより、IPアドレスヒントを含むことができる
  - [SHOULD] これらを受信した場合、TargetNameに対応するAレコードとAAAAレコードがまだ利用できないときは、
    アルゴリズム上、肯定的で空でない応答とみなすべき
    - クライアントは、それらのTargetNameに対するレコードをまだ受信していない場合、
      依然としてAおよびAAAAの問い合わせを発行する必要がある
      - それらのレコードを受信したときは、ヒントを置き換え、利用可能な応答の集合を新しい応答として更新する (4.3)
